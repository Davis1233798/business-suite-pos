# POS held-cart cashier slice

## Architecture

Go owns held-cart state, organization/store/shift authorization, claim locking, current catalog values, discount validation, checkout totals, inventory, audit, and idempotency. React owns only the active cashier's temporary basket and pending operation inputs. The held-cart controls extend the current `/pos/front` flow and use the authenticated same-origin Go API. They do not read the generic POS back-office dataset.

The existing `POST /api/stations/pos/cart` handler implements `hold`, `claim`, `release`, owner-only `update` and `discard`, and held-cart `checkout`. A scoped read is provided at `GET /api/stations/pos/held-carts?shiftId=...`; `GET /api/stations/pos/cart` is not a read API, `/api/stations/pos/terminal` returns only registers and the caller's open shifts, and the generic front view omits held carts. The held-cart list:

- Requires an enabled POS grant and an open shift. A normal operator may read only their own shift; an administrator may use a shift they are already authorized to operate, matching the existing cart action rules.
- Resolves the store from that shift on the server. It does not accept a caller-supplied organization or store as authority.
- Returns only carts with `status='held'` in that store plus carts with `status='retrieved'` whose claim is owned by the current user. This lets a cashier recover their own claim after a page reload. Other users' claims and completed carts are omitted, as are carts from other organizations and stores. Return the status but never the `locked_by` value.
- Uses bounded keyset pagination: `GET ...?shiftId=<id>&limit=50&cursor=<token>` returns `{items,hasMore,nextCursor}` in the `data` envelope. The default page size is 50 and accepted values are 1–50; invalid or oversized limits return 400. Owner-held `retrieved` carts sort before shared `held` carts, then by `held_at` and ID. The cursor records that deterministic position and is bound to the requesting organization, store, shift, and user. No unbounded count or row read is performed. The optional `cartId=<id>` targeted read returns at most one eligible row in the same envelope, allowing an owner to refresh a known claim after pagination without exposing other claimants' carts.
- Each entry contains only `cartId`, `cartName`, `heldAt`, `status`, and stored item IDs, quantities, and fixed line discounts. Include current catalog display/price/stock/active state needed to restore the basket, resolved by the server; mark unavailable items explicitly. Never expose `locked_by`, organization IDs, raw account data, or unrelated records.
- Returns HTTP 400 when `shiftId` is missing or malformed, 403 for a read-only role or non-admin reading another cashier's shift, 404 when the shift is missing, closed, or belongs to another organization, and 503 for storage or invalid persisted-cart failures.
- Treat the listed price as an estimate. Checkout re-resolves current catalog state and remains authoritative. A disabled/missing item or a price change that invalidates a stored discount must produce a clear correction error without changing stock, sale, or held-cart state.

## Operation and retry boundary

- **Hold:** POST `{action:"hold", shiftId, cartName, lines:[{itemId,quantity,discountAmount}], idempotencyKey}`. Require a non-empty named basket. Clear the local basket only after confirmed success. For network/5xx ambiguity, preserve and freeze the submitted payload and retry with the same key.
- **Claim:** POST `{action:"claim", shiftId, cartId, idempotencyKey}`. The server transaction permits one claimant. On success, restore the cart's item IDs, quantities, and discounts from the successful read snapshot; the returned items remain display estimates. On 409, refresh the held list and report that another cashier claimed it. For ambiguous results, replay the identical key and request.
- **Resume:** A list entry with `status='retrieved'` is visible only to its claimant. Restore that entry's persisted item IDs, quantities, and discounts directly without trying to claim it again. This recovers the cashier's working cart after a reload; another user never sees or resumes that claim.
- **Release:** POST `{action:"release", shiftId, cartId, idempotencyKey}`. Only the claimant can release. Remove the restored basket only after confirmed release and then refresh the list. Preserve the same request key and inputs through ambiguous outcomes.
- **Correct held lines:** POST `{action:"update", shiftId, cartId, lines:[{itemId,quantity,discountAmount}], idempotencyKey}`. Only the claimant may update a retrieved cart. The server resolves active catalog products and validates each fixed line discount against current gross before atomically replacing the stored lines; it does not deduct stock. A successful update keeps the cart retrieved and owned by the same cashier. Use this operation after a stale-price checkout rejection so a cashier can reduce an invalid discount and persist that correction before retrying checkout. Ambiguous outcomes reuse the identical request key and payload.
- **Discard unusable cart:** POST `{action:"discard", shiftId, cartId, idempotencyKey}`. Only the claimant may discard a retrieved cart. The transaction marks it `cancelled`, clears its claim, records audit/idempotency, and does not create a sale or change stock. The cashier UI should request explicit confirmation before discarding; cancelled carts are never listed again.
- **Checkout:** POST the existing `{action:"checkout", shiftId, cartId, tender, idempotencyKey}` contract. The backend ignores client-supplied lines for held carts and uses the persisted line snapshot. It requires the current user to own the claim, rechecks current prices, discounts and stock, then atomically records the sale and marks the held cart completed. Receipt values come from the server.
- Disable edits and conflicting actions while an operation is pending or ambiguous. Each pending operation owns its stable idempotency key and immutable payload; clear it only on confirmed success or definitive client rejection. Refresh the held-cart list after confirmed hold/claim/release/checkout and after a claim conflict.

## Test-first acceptance

1. API tests cover the held list's own-shift access, administrator access boundary, foreign organization/store exclusion, other-user claimed-cart exclusion, current-user recovery rows, recovery-first ordering across pages, bounded page size, no duplicate or missing rows across cursors, cursor binding to organization/store/shift/user, owner-only targeted reads, and absence of `locked_by`/organization identifiers. Missing/closed/unauthorized shifts and malformed/oversized pagination requests are rejected.
2. Existing Go cart tests continue to prove one winner in a concurrent claim race, idempotent replay, foreign claimant checkout denial, transactional sale/stock/cart completion, and held discount authority. API list tests cover owner-only recovery entries and prioritize them within the bounded list; update tests cover claimant ownership, current-price discount validation, exact replay/payload conflict, stock neutrality, and server-authoritative checkout after correction. Discard tests cover claimant-only access, idempotency/audit, list removal and unchanged sale/stock state. Failed stale-price/disabled-item checkout must leave stock, sale rows, and cart status unchanged.
3. Browser tests hold a named discounted basket, see it disappear from the active basket and appear in the held list, claim it, verify quantities/discount restore, release it, and verify it is listable again. Re-claim and checkout show the server receipt and remove the completed cart from the list. An owned claimed cart survives reload; stale discounts are corrected through an owner-only server update; unusable claimed carts can be explicitly discarded after confirmation.
4. Two independent browser contexts share mocked server state and race to claim the same held cart. Exactly one claim succeeds; the loser receives conflict, refreshes the list, and cannot checkout the other's claim. Verify read-only and foreign-store views cannot claim or reveal the cart.
5. Inject ambiguous 503/network outcomes for hold, claim, release, and discard. Retries must send byte-equivalent logical payloads and the same idempotency key; only confirmed outcomes change visible basket/list state. The update path must also preserve its exact payload/key when retrying an ambiguous response.
6. Run focused Go tests, `npm test`, the cashier Playwright spec, `npx tsc --noEmit`, `npm run web:build`, and `git diff --check`.

This slice completes the cashier UI path for P04 only. It does not claim offline sales, cross-store cart transfer, automatic expiry, full P01–P08 verification, identity mapping, production migration, or deployment.
